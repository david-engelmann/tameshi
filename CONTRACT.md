# tameshi contract

This contract is the executable spec for tameshi. Every obligation below maps to at least one named test in the test suite. An obligation is met only when its tests pass.

## Ground and probes

Tameshi judges checks, verdictloop judges changes. Tameshi is the evidence pack tool for checks. It assembles the evidence the gate instruments produce into one evidence pack per check and issues the ruling on a check as a pull request. It reads local files only and never reaches a network in the tool or in its tests, and it deletes nothing.

The catchledger probe ran the catchledger command line from its own repository on its committed synthetic examples and read the emitted files. The probe found one ledger document whose format name is catchledger-ledger/1 and one pack file per check whose format name is catchledger-pack/1. A catchledger pack carries exactly nine fields, which are the format name and the repository label and the check name and the scorecard and the catch record and the canaryfield results and the false block rate and the pricing record and the source record. The scorecard carries exactly thirteen fields, which are fires and blocks and judged commits and flaky commits and flake rate and runtime seconds and runtime minutes and catches and false blocks and unattributed blocks and false block rate and total cost and cost per catch. A ledger carries one entry per check and each entry carries exactly the check name and the scorecard and the catch record and the canaryfield results and the evidence pack file name. Catchledger rebuilds each pack from its ledger entry field for field, and a supplied pack that differs from the rebuilt pack in any field is refused there. Tameshi mirrors that exactness on its own pack.

The catch record probe found that each catch record entry carries a started at timestamp in UTC with a trailing Z and that those timestamps are the only per check time evidence a catchledger pack holds. The floor ground below therefore measures the CI history leg in distinct UTC calendar dates among a check's catch record timestamps. That reading is a limit of this slice and it is stated here rather than hidden in the code. A check whose blocks are few or compressed into few distinct dates reads below the floor on the CI history leg even when the check ran on more days, and widening the window source is later work.

The canaryfield probe read the catch table shape that catchledger validates and the normalized shape catchledger emits. A catch table carries a gates list and rows, and each row carries a seed and a name and a defect class and planted files and a result for each gate. The result words are caught and waved-through and not-applicable and gate-broken. Catchledger normalizes a matched gate into counts over the four words and the matched rows sorted by seed. A planted defect counts as scored for a check when the table carries a result for that check's gate and the result is not not-applicable, because a not-applicable row never exercised the gate against the defect.

The floor ground is set by the program and stands above any single repo. No ruling issues on a check whose evidence holds fewer than 30 canaryfield-scored planted defects or fewer than 14 days of catchledger CI history. This slice builds the pack format and the ruling generator only. A pack below the floor is assembled and marked below floor, and the generator refuses to issue a ruling from it.

The blindgate ground is narrower. No published blindgate evidence format stands in the program yet, so this slice accepts blindness evidence in the shape stated here and carries it into the pack. The accepted shape is a document whose format name is blindgate-evidence/1 and whose traces list carries one object per trace, each holding a check name and a surface and an observation and a detail, all as nonempty text. Alignment with a published blindgate format, when one stands, is later work.

The decision model ground is a limit and not a build. The roadmap places a decision model at the ruling layer in later work. This slice builds no model call and the pack carries no recommendation record, and that absence is stated here so no reader mistakes the deterministic floor and generator for the finished tool.

## Amendment to the CI history ground

This amendment names and replaces two earlier readings in this contract. The catch record probe paragraph above states that the CI history leg is measured in distinct UTC calendar dates among a check's catch record timestamps, and obligation KK2-5 states that the CI history leg counts those distinct dates. Both readings are replaced by the window reading here, and the earlier text is left standing so the record shows both.

Catchledger now publishes a history window record in its ledger and in every pack. The window carries the earliest and latest timestamps among the runs the ledger ingested for the check, and it stands null when the run set is empty. The CI history leg reads that window. The leg counts the UTC calendar days the window spans, from the date of the earliest run through the date of the latest run inclusive, so a window whose latest date stands thirteen days after its earliest date holds fourteen days of history. A pack whose window is absent or null holds zero days of history and reads below the floor on that leg, which is the safe direction while packs written before the window stood are still in circulation. Each tameshi pack carries the window record exactly as its catchledger pack carried it, under the name history window, and the generator recomputes the leg from the window standing in the pack it is asked to rule on. Obligation KK2-1 is read with this amendment, so a catchledger pack or ledger entry may carry the history window record beside the probed fields and no other field beyond them. Proven by test_floor_counts_history_days_from_the_window_span and test_a_pack_without_a_history_window_reads_zero_history_days, alongside the floor tests named in obligation KK2-5.

A correction to that amendment stands here, now that the catchledger fix has landed and its shape is read from its contract and code rather than awaited. The amendment above says the window carries the earliest and latest timestamps among the runs the ledger ingested for the check, and that a ledger entry may carry the window beside the probed fields. Both phrases are corrected. The window is one record across every ingested run, holding the first run start and the last run update, and the same record stands in the ledger and in every pack, so the CI history leg reads the span of the whole ingested history a pack rests on, including for a check with no blocks of its own. The window stands at the top of the ledger and at the top of each pack under the name history window, with its two timestamps under the names first run started at and last run updated at, and a ledger entry carries no window of its own. The reading rule is unchanged, and an absent or null window still holds zero days.
